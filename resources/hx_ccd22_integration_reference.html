4.1 — Heartbeat payload (camera sends this TO you)

{
  "sn": "2100002507152593",   // device serial number — your primary key
  "time": 1751234567           // UNIX timestamp from camera clock
}

4.2 — Heartbeat response (you send this BACK to camera)

Critical: camera expects this response or it may retry. Return server time so camera can sync its clock.

{
  "code": 0,              // 0=success, 1=SN not found, 2=other error
  "msg": "success",
  "data": {
    "sn": "2100002507152593",
    "time": 1751234567      // your server time — used by camera for time sync
  }
}

6Camera config parameters that affect data quality

Height (critical)

Must match actual installation height within ±5cm. If wrong, counts will be off. Bus version supports up to 3.0m (covers 7.14m width).

Filter height (recommended: 100-120cm)

Objects below this are ignored. Prevents luggage, bags from being counted. Set this before you trust any counts.

Detection area (red box)

Must cover only the door ground area. Too wide = counts people sitting in seats. Draw it carefully.

Detection line (green line)

Should be centered in the detection area. Direction of arrow = "enter" direction. This is what makes in vs out.

Child mode

Off by default. Enable in settings. Child = height between filter threshold and child threshold. Height-based only, not actual age.

Upload interval

Set to 1 or 5 minutes. 0 = real-time. For 2000 buses at 1 min = 2000 POST requests/min to your backend. Design accordingly.

8Recommended tech stack

Backend API

FastAPI (Python) — fast to build, async, easy Pydantic validation of incoming payloads.

Database

PostgreSQL + TimescaleDB extension for time-series queries on passenger_counts at scale.

Dashboard

React + Recharts. Or Grafana on top of PostgreSQL for a fast MVP without building UI from scratch.
